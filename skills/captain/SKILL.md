---
name: captain
description: Coordinate a project across persistent crew threads, inspect its digest, or delegate an isolated writer when the user asks for a Captain.
---

Use the local `pa thread captain` commands with `await bash(command)` in the Prime Python kernel.
Use `pa thread captain status` to find the current project ID and read its plan, crew, and decisions.
Keep other project records out of the answer unless the user asks about multiple projects.

For a requested state change, run `pa thread captain act OP` and pass a JSON object on stdin.
Use the current workspace as cwd.
For a read-only assignment, a shell command can use `printf %s '{"provider":"prime","model":"openai-codex/gpt-5.3-codex","task":"Review the parser","write":false,"request_id":"review-parser"}' | pa thread captain act delegate`.
Quote dynamic JSON as shell data. Within a Python cell use the harness bash helper for shell commands.
When the Captain has supplied an executable and explicit environment, use that command.
Use the returned job or crew ID to track progress.

- `init` takes `brief` in the current checkout, and optional `provider` (prime, claude, codex, antigravity, cursor), `model` (from `pa model list`, `pa thread models antigravity`, or `pa thread models cursor`), `thinking` (default, off, minimal, low, medium, high, xhigh, max), `parallel`, and `crew` (thread references). It queues the Captain's first turn, which writes its plan, rules, crew rules, and digest. With `design: true`, a design request for a project factory follows that turn. Use `lead` with `text` to send a request to the persistent lead.
- `promote` takes `ref` (a root thread ID, a native session path, or `current`) and `brief`. The thread becomes the Captain and keeps its history.
- `stop` takes `project`. It cancels queued jobs, stops running crew turns and Captain-started factory runs, and pauses the Captain so no new turn starts, including digest wakeups. `resume` takes `project` and starts work again. `delete` takes `project`, stops everything first, and removes the Captain's project record; the lead thread, crew threads, transcripts, and worktrees stay (`demote` is the same action). Use these only when the user asks. The CLI shortcuts are `pa thread captain stop|resume|delete [project]`. Only the user's own chats can run them; a Captain, crew, or factory session is refused.
- `edit` takes `project`, `field` (plan, rules, crew_rules, digest, objective), and `value`. The user can also edit name, parallel, model (`provider` plus `value`), and `thinking`. Each edit is recorded with its author and the previous text. Rules, crew rules, plan, and digest are mirrored to `<project>/.prime/captain/AGENTS.md`, `CREW.md`, `NOTES.md`, and `DIGEST.md`. `edit-history` (optional `field`) lists edits; only the user runs `edit-restore` with `edit_id`.
- Write a standing rule from the user into rules (Captain only) or crew_rules (every crew turn), keep the existing rules, and confirm in one line. Rewrite the digest after crew changes as Needs you, New, and In progress.
- `adopt` takes `project` and `ref`, a root provider thread ID or native Prime session path. Use the saved Prime continuation for imported history.
- `delegate` takes `project`, `provider`, `task`, `write`, a stable `request_id`, and optional `model` and `thinking`. Prefer `provider` prime with a pa model, such as `anthropic/claude-opus-5-5` (Claude through its CLI), `openai-codex/gpt-5.3-codex`, or `antigravity/gemini-4-neon`: the crew thread is then a native pa chat that the user can open, read, and reply to. Providers claude, codex, and antigravity run their own CLIs. Use an independent worktree for edits. For dependent changes, pass the accepted commit as `base`.
- `delegate` with `machine` and optional `model` and `thinking` sets the model of steps that name no model or role for that run; without them those steps run on the project's factory default.
- `delegate` with `machine` starts a factory run instead of a crew thread: `{"machine":"code-review-sweep","task":"Review the parser","request_id":"review-1"}`. Optional `params` must match the machine's parameters; `task` fills the first required text parameter. The run needs no open chat, uses one parallel slot, and reports when it pauses or ends. A writer machine gets its own worktree and accepts `base`.
- A machine is read-only when its folder has `captain.toml` with `access = "read"`; any other machine writes code. The Captain may start a read-only machine on its own. For a writer machine it asks with NEEDS YOU: and passes `approved: true` in the turn where the user agrees. That works only in a turn that answers a user message, never in a turn started by a crew event. A refused writer request is kept as a pending grant under Needs you; the user approves it there (`grant-approve` with `grant_id` and optional `standing: true`, which also grants the machine) and the run starts at once with no Captain turn, or declines it (`grant-decline`). Only the user can do either.
- `grant` takes `project`, `machine`, and optional `allow` (default true). Use it when the user gives standing permission for a writer machine, in that same turn, and also write the rule into `rules`. A granted machine starts without asking. `allow: false` revokes it.
- Project factories: the Captain may write or change a factory at `<project root>/.prime/machines/<name>/` (lowercase name, not a library machine name). Read `rlm.factory.help()` for the format, then run `factory-validate` with `name` until it is valid. `factory-show` returns the compiled graph, the digest, and the state: missing, invalid, draft, approved, or changed. Start one with `delegate` and `machine` only when it is approved. The user approves one exact version in the Captain panel (F6, then F); any edit makes it a draft again, so after a change tell the user under Needs you that it needs review. You may edit a factory while a run of it is live: every run executes from its own frozen copy of the approved files, so an edit never changes a run in flight. Python nodes run code, and the approval covers them. `factory-approve` takes `name` and `digest` and works only in a turn that answers a user message; only the user deletes a factory. The Captain may request a design itself with `factory-design` (`text`, `request_id`) when the plan needs a repeatable pipeline; a design turn cannot request another. A design request turn writes and validates a factory and never runs it; the runtime refuses `rlm.factory.run` on a project factory folder.
- Before designing a factory, read `references/fsm-design-guide.md`: when to use an FSM, the exact `machine.toml` format, CLI-backed vs native outputs, and archetypes (delivery, delegation/router, consensus, research verification, read-only audit, staged refactor). Choose models only from the Configured models list in your context.
- Factory models are policy, not content. When the user asks to change FSM models or thinking (for example "change all the fsm subagents to argon and use high thinking"), immediately run `factory-set-model` with `{"name":"<factory>","all":true,"model":"antigravity/gemini-4-argon","thinking":"high"}`, or with `role` or `state` for one target (neither sets `[roles].default`). Do not punt to `AGENTS.md` and do not wait for a live run. The choice is stored in the project's model overlay: the factory stays approved, the review page and FSM chart show it at once, and runs that start afterwards use it. Optional `sync_specialists: true` also writes it into the specialists those states use (that is an edit, so the factory needs approval again); `persist_to_toml: true` writes machine.toml instead. `factory-clear-model-override` (`role`, `state`, or `all: true`) goes back to machine.toml. The user or a turn that answers a user message can run both; digest, brief, design, and crew turns cannot.
- When the user asks to change FSM structure, stages, modules, or specialists, edit the factory right away, even while a run is live (`factory-compose`, `factory-add-stage`, `factory-remove-stage`, `factory-add-module`, and the others work in a turn that answers the user). When the user pre-approves the change in that message ("I preapprove it, don't wait for me"), run `factory-preapprove` with `name` (or `"*"` for every project factory; `allow: false` revokes), make the edit, run `factory-show` for the new digest, and run `factory-approve` with that digest in the same turn, so the next phase starts without waiting. `factory-approve` also accepts `preapprove: true`. Without a pre-approval, a turn cannot approve its own edit: tell the user under Needs you.
- Always pass a short human-readable `title` on `delegate`, for crew threads and factory runs alike, so rows show a name instead of a hash.
- Shared modules: `factory-modules` lists factory parts (`review-triad`, `sanitize-diff`, `validate`, and user modules in `~/.prime/agent/modules/`). `factory-add-module` takes `name`, `module`, optional `alias`, `wire` (the module's placeholders, for example `{"subject":"build.summary","approve":"ship","rework":"build"}`), and `after` (states whose `next` becomes the module entry). It copies the files to `modules/<alias>/`, adds the states as `<alias>-<state>`, and records `modules.lock`. `factory-update-module` takes `name` and `alias` when the review shows "module update available". Both are edits, so the user approves again.
- Project specialists: `specialist-write` takes `id`, `name`, `description`, `model`, `thinking`, and `prompt`, and writes `<project>/.prime/agents/<id>.md`; the Captain writes one in a turn that answers the user, a design turn, or a turn that reviews crew reports. A design turn writes the specialists the project needs, for example an ML theory verifier. `factory-use-specialist` takes `name`, `specialist`, and `states`: it adds the role and puts the prompt in each state's prompt file. When a specialist changes, the factory shows "specialist changed - update"; run `factory-update-specialist` and ask the user to approve again. When the user deletes a specialist that a factory uses, the factory shows "specialist missing - write it again"; write it again, then update the factory. `delegate` accepts `specialist` to give a crew thread its prompt, model, and thinking. `specialist-list` and `specialist-show` read; only the user deletes a specialist.
- `answer` takes `project`, `member` (a paused run), `text`, `decision` (resume or stop), and a stable `request_id`. On resume, `text` reaches the retried step as a reviewer note; omit it for a plain retry. One answer resumes a pause once; a repeated request ID returns the first result.
- `reply` takes `project`, `member`, `text`, and a stable `request_id`. `release` removes membership and keeps the thread. `archive` and `unarchive` take `member` and hide or show a finished thread; its transcript and worktree stay.
- Use a machine when the procedure is known and has verification gates (build, review, validate, or a two-model decision on a plan). Use a crew thread for open-ended work. The user's `consensus` action (with `task`) starts dual-consensus directly, and a library factory chosen in setup starts as soon as the Captain is created. For an explicit two-model decision, delegate the dual-consensus machine with the question as `task`. Report disagreement when the votes do not agree.
- If a worker is interrupted, inspect its thread and checkout before a retry. Its first attempt can already have changed files. A daemon turn that finished after its worker died is recovered from its native session once the daemon is idle. `pa thread captain reconcile` settles interrupted work and is safe to repeat.
- When a writer's worktree folder was removed outside pa, its row shows `worktree_missing` and a Needs you item; only the user runs `worktree-recreate` with `member`, which puts the worktree back on branch `pa/<member>` (or its base commit when the branch is gone) without discarding work.
- `status` lists every human gate of a project in `needs_you` (kinds captain, paused_run, draft_factory, changed_factory, pending_grant, blocked_crew, worktree_missing); the panel's count is its length. Crew rows carry `activity_state` (working, waiting, failed, idle), `needs_you`, `archived`, `updated_at`, and worktree `diff_added`/`diff_deleted`; a Captain-started run also carries `host_session`, `run_id`, `graph`, and `step_sessions`.
- To make the user pick between options, run `escalate` (`title`, `summary`, `recommendation`, `options` of `{key, label, reply_text}`) instead of a prose wall; the panel shows a card the user answers with one key.
- `wake-policy` (`policy`: per event `react`, `context`, or `ignore`), `schedule-add`/`schedule-list`/`schedule-toggle` (cron tasks), `pr-watch` (a crew PR's CI and reviews), and `budget` (cap or extend spend) change project policy. For stacked branches, pass `depends_on` (the parent member) on `delegate`.
- Crew reports and handoffs are saved in `.prime/captain/reports/` and `.prime/captain/handoffs/`; status carries pointers. Read a full file only when you need it.
- In pa, F6 or `/captain` opens the Captain panel; Enter opens the Captain or a crew thread in the normal chat. In a Captain chat, F7 or `/crew` switches between the Captain and its crew, and Shift+F7 or `/captain chat` returns to the Captain. A message typed in the Captain's chat is a Captain turn, the same as `lead`. The panel keys are s stop, R resume, D delete, and F project factories (review, approve, or request a design).
- Prime Captain and crew turns run on the user's daemon, so their chats open live with their subagents while a turn runs. A message typed in the Captain chat during a turn waits and runs as the next Captain turn.
